## ⚠️ THE OPEN BUG: the hang, captured live at 11:20-11:30

The steward reported the GUI hung while `tier=hart-comp` with the iGPU compositing.
**Captured before restarting.** This is the best evidence the session produced:

```
hart-comp   State: S (sleeping)   wchan: do_epoll_wait   ~0% CPU   up 767s
WebKit      State: S (sleeping)   wchan: ppoll           2.3% CPU
D-state processes : NONE
kernel i915/DRM   : NOTHING in 6 minutes
session log       : NOTHING in the last 5 minutes
backends          : 6800 and 6777 both 200 in ~2ms
memory            : 8.7G available      loadavg 3.50
temp 94C, cpu0 2062MHz
still holds: 5 fds on /dev/dri/card1, 8 fds on /dev/input/event*
atomic state: plane[32] primary A, crtc=pipe A, fb=103   (valid scanout config)
```

**This is a LOST WAKEUP, not a spin, not a crash, not thermal, not OOM.** The
compositor is parked in `epoll_wait` waiting for an event that never arrives, while
holding a perfectly good scanout configuration.

### SOLVED, 11:34 — it is I/O STARVATION ON THE USB2 BOOT STICK

Ten minutes later the steward started a Flatpak install ("stuck past 75%"), and the
D-state list gave the whole answer:

```
   271 D   usb_sg_wait               usb-storage              <- USB2 stick jammed
   312 D   jbd2_journal_commit_tr    jbd2/sdc2-8              <- root fs cannot commit
348238 D   blk_mq_get_tag            kworker flush-8:32
422112 D<  drm_atomic_helper_wait    kworker/u33:0+i915_flip  <- THE PAGE-FLIP WORKER
423142 Dl  wb_wait_for_completion    flatpak
disk free 1.2G   wifi rx=528MB   loadavg 6.79
```

**The i915 flip worker is blocked in `drm_atomic_helper_wait`.** That is precisely why
hart-comp parks in `epoll_wait`: its page-flip completion can never be delivered. The
flip worker is stuck because the block layer is jammed behind a saturated USB2 stick
that carries the root filesystem, with the disk nearly full.

This retires the whole freeze investigation and explains every symptom the session could
not:

* **No CPU spin, no crash, no OOM** — correct, it is D-state I/O wait.
* **"The mouse still moves"** — input and the cursor plane are unaffected while the
  flip worker is blocked.
* **"It stalls after a period"** — it stalls whenever something writes hard to the
  stick (Flatpak pulls, journal export, SmartFS indexing, WebKit cache).
* **Never thermal.** Confirmed again: 94C throughout, and 94C when fine.
* **The compositor was innocent all along**, exactly as the Tier-1 RCA found for the
  other failure.

**Implication for the fixes:** the CAP_SYS_ADMIN/DRM-master work is still correct and
still needed (A/B-proven), but it was never the freeze. Two independent faults wore the
same face.

**What to do about it** (none of this is done yet):

1. **Get the root filesystem off USB2**, or accept the ceiling. This is the real fix.
2. **Stop the OS writing to the stick during interactive use.** Prime suspects already
   identified this session: `hart-journal-export` (fixed to one write, `ca76246`), the
   SmartFS indexer walking `/home` every 5 minutes, and Flatpak pulling to
   `/var/lib/flatpak` on the same device.
3. **Give the flip path priority, or the writers less.** `IOSchedulingClass=idle` on
   the background writers (already done for `hart-journal-export` and `clamav-daemon`)
   should extend to the indexer and the installer.
4. **Watch for it:** a D-state process on `drm_atomic_helper_wait` is the fingerprint.
   `ps -eo pid,stat,wchan:24,comm | awk '$2 ~ /D/'` is the single cheapest check, and it
   is now the FIRST thing to run on any future freeze.
5. **Disk was at 1.2G free.** Low space makes this dramatically worse. Check it early.

**One caution about my own reading:** I first noted `Active=no State=online` and nearly
blamed a logind session deactivation. That `awk` picked the FIRST line matching `seat0`,
which is the stale **tty1** session, not the compositor's tty7 one. It was a red herring.
Query the compositor's own session explicitly if you ever need it.

## FIXED AT SOURCE, NOT VERIFIED — do not report these as done

* **`58acd09` numpad (Rust).** The env-only fix shipped in `ca76246` **did not work** —
  the steward tested it and the keypad still typed direction keys. Root cause:
  `XkbConfig::default()` looks like it defers to libxkbcommon's env defaults and does
  not; `options: None` becomes an **empty CString** (non-NULL), and libxkbcommon only
  consults `XKB_DEFAULT_OPTIONS` when the pointer is NULL. Proven by reading the keymap
  hart-comp was actually serving out of `/memfd:smithay-keymap`. Now read explicitly in
  `compositor/src/shared.rs::XkbEnv`. **Never compiled.** See NEXT ACTION.

  bind-mounted `setcap`'d copy; the wrapper path has never run on real hardware.

## METHOD NOTES — traps that cost real time today

* **Read the SERVED artifact, not one you compiled yourself.** Every check said the
  numpad fix was in place; only the keymap hart-comp was actually serving
  (`/memfd:smithay-keymap`, via `/proc/PID/fd`) disagreed, and it was the one that
  mattered.
* **Tier output goes to `session-<id>.scope`, NOT `greetd.service`.** Grepping
  `-u greetd` hid hart-comp's own words for hours. Use `journalctl --since` with no unit
  filter.
* **`head -1` on a Nix store glob is a trap.** It picked the i686 libglvnd (ELFCLASS32)
  and cost the whole EGL detour. I then made the same mistake again with
  `xkeyboard-config`. Always assert what you selected (ELF class, file present).
* **greetd builds a fresh session env through PAM.** A unit-level `Environment=`
  drop-in never reaches the tier (measured). Patch the **session-selector** script.
* **`first-scanout` is NOT proof of DRM master** — proven today: with `drmSetMaster`
  refused, hart-comp still logged a completed page-flip vblank. Use the explicit
  `acquired DRM master` line.
* **`ps` `pcpu` is a lifetime average**, not instantaneous. Use `top -b -n 2` and read
  the SECOND sample.
* **Never `journalctl -b` / `dmesg` in a loop on this box** — it pegs a core and heats
  the machine you are measuring. Twice misread as a system fault. Use `-n N`/`--since`.
* **Change one thing at a time.** The socket fix works but is not isolated because I
  bundled three changes into one run.
* **This chassis sits at 93-95C in every state measured.** Temperature is not a signal
  here; the CLOCK is (1197 -> 2892MHz depending on load).
